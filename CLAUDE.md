# dev-tools

## Developer setup

This repository ships a repo-local git hooks directory at `.githooks/` and a companion `scripts/` directory for parity enforcement on shared command-file blocks. Together they gate commits that touch the flow-command files enumerated in the manifest. Enable the hook dir once per clone:

```bash
git config core.hooksPath .githooks
```

The pre-commit hook invokes `scripts/verify-shared-blocks.sh`, which reads its parity manifest from `scripts/shared-blocks.toml` and checks that each named block remains byte-identical across every file that carries it. After the progressive-disclosure overhaul (wave 2, 2026-05-20) the manifest carries exactly ONE block: `forbidden-working-tree-ops`, spanning the two implement agents `claude/agents/implement-{deep,lite}.md`. The ten former command-blocks (`flow-context`, `ledger-schema`, `execution-record-schema`, `ledger-disposition-sweep`, `plansdirectory-prompt`, `vet-research`, and the four `apply-*` blocks — `apply-dependency-sort`, `apply-rollback-protocol`, `apply-constraints`, `apply-vet-implement-lite`) were removed from the manifest once the command carriers stopped embedding them. See `scripts/shared-blocks.toml` for the canonical per-block file list — widening or narrowing a block's coverage means editing that manifest, not this prose. The hook fires on every commit and the verifier inspects only the files named in the manifest, currently just `claude/agents/implement-{deep,lite}.md`; commits that touch only files outside the manifest are unaffected.

Do not bypass the hook with `--no-verify` on these files — drift in the `forbidden-working-tree-ops` block between the two implement agents would let the deep/lite implementers diverge on which working-tree operations are orchestrator-only, the kind of contract drift that has historically caused duplicate-finding cycles in the review/optimise ledger. The five command carriers (`optimise`, `optimise-apply`, `review-apply`, `plan-update`, `test-bootstrap`) no longer embed shared blocks at all: they were skeletonised to invoke the `flow-contract-*` skills (and the `apply-*` skills), so blocks such as `flow-context`, `ledger-schema`, `execution-record-schema`, and `plansdirectory-prompt` now live in exactly one skill body each and are single-source — there is no embedded carrier copy left to drift against. Consequently the `tomlctl blocks verify-skills` cargo test (`verify_skills_clean`) is presently DORMANT: with no hybrid block (one carrying both `skill=` and a non-empty `files=`) the engine checks zero blocks and passes vacuously. Skill↔carrier drift protection reactivates only if a future wave re-embeds an externalised block into a carrier; until then, drift cannot occur because each block has a single home. (Carrier invocation of the externalised skills is separately guarded by the `carrier_invokes_required_skills` cargo test.) (`forbidden-working-tree-ops` is the exception that stays inline: the two implementer agents have no Skill tool, so they embed it directly — and `claude/agents/verification.md` also references it without being parity-checked, so the byte-identity guarantee covers only the two agents named in the manifest.) If the script refuses your commit, fix the drift rather than skipping the check.

**Note**: if `.githooks/` is absent (hook dir not installed), the shared-block parity check simply won't run. But if `.githooks/pre-commit` is installed and `scripts/verify-shared-blocks.sh` is missing, the hook fails loudly and rejects every staged commit until the script is restored. Run `ls .githooks scripts` to confirm both are present before relying on the hook.

**Supply-chain note**: once `core.hooksPath` points at `.githooks/`, every commit runs `.githooks/pre-commit` and everything it invokes (currently `scripts/verify-shared-blocks.sh`). Review PR diffs touching `.githooks/**` or `scripts/verify-shared-blocks.sh` with the same scrutiny you'd apply to an unsandboxed CI step — a malicious commit to those paths runs on your next `git commit` without confirmation.

**Windows note**: `scripts/verify-shared-blocks.sh` requires GNU awk. The default Git Bash for Windows ships mawk, which is not compatible. Install GNU awk via `pacman -S gawk` (MSYS2) or `scoop install gawk` (Scoop) before relying on the pre-commit hook.

## Flow agent tiers (`lite` / `deep`)

The flow subagents under `claude/agents/` follow a `<purpose>-<strength>` naming convention and split into two capability **buckets**:

- **`lite`** (`research-lite`, `implement-lite`) — the fast/cheap route for simple, well-defined work: mechanical fetch-and-summarise research and fully-specified, low-coupling edits.
- **`deep`** (`research-deep`, `implement-deep`) — for complex, critical, or judgement-heavy work: architectural reasoning, ambiguous specs, cross-file refactors, security-sensitive code.

The model and reasoning effort behind each bucket live **only in the agent's frontmatter** (`model:` + `effort:`) — that is the single place to retune a bucket. Prose throughout the repo refers to agents by name (`*-lite` / `*-deep`) and never hardcodes a model, so retuning a bucket needs no prose changes. Current settings: both buckets use the `opus` model alias (which always resolves to the latest Opus) — `lite` at `effort: medium`, `deep` at `effort: high`. To change what a bucket costs, edit the two `*-lite` (or two `*-deep`) frontmatters; nothing else needs to move.

`flow-bootstrap` (flow resolution + doctor) and `verification` (sequential command runner) are fixed `haiku`-alias utility agents that sit outside the lite/deep buckets.

## Build discipline in multi-agent flows

During a flow (`/implement`, `/optimise-apply`, `/review-apply`, `/tdd`), implementer and research sub-agents must NOT run full builds or test suites to self-verify their edits. `cargo build`/`cargo test`/`cargo nextest` are expensive, and N parallel agents each invoking them against the SHARED `tomlctl/target` or `lumina/target` directory serialise on cargo's build lock and thrash the incremental cache — repeated, redundant whole-crate rebuilds are the cost this discipline exists to cut.

- **Sub-agents** (`implement-lite`, `implement-deep`, `research-*`): reach for `cargo check`/`cargo clippy` (or, for the SPA, `bun run type-check`) to confirm a non-trivial edit type-checks, and run the task's OWN narrow/scoped test when its `Acceptance` calls for one — `cargo test --test <name>` (compiles just that one binary, the cheapest narrowing) or `cargo nextest -E 'test(<area>)'` (compiles the test bins but runs only the matched tests). Keep it light — prefer reasoning over re-checking, and skip checks for edits you can reason about confidently (docs, comments, a localised rename). Do **not** run a full `cargo build` or the whole `cargo test`/`cargo nextest`/`bun run build` suite — those belong to the verification step. If a check fails for a transient/environmental reason (e.g. a Bash fork flake), do not retry-loop or escalate to a full build: note it (`[vet-recommended]` for lite clusters) and return so the orchestrator's verification pass becomes the source of truth.
- **The orchestrator** owns all building and testing, at two tiers — never per sub-agent — via the `verification` agent (`claude/agents/verification.md`): (1) **at each batch commit checkpoint**, it builds the touched crate and runs that crate's full test suite *before* committing, so every commit is non-broken and bisectable; (2) **a final full pass** (build + tests + lint + audit) in the command's Phase-3 verification. The full `cargo build` / whole `cargo test` / `cargo nextest` suite / the SPA bundle build belong to these orchestrator tiers — even when a task's `Acceptance` names a whole-suite command (that's the orchestrator's checkpoint responsibility); a narrow per-task test, by contrast, the delegate runs itself.

The per-crate command lists below are the menu for that orchestrator-run verification step (and for a human at a terminal) — they are NOT a per-edit checklist for sub-agents.

### Inner-loop vs full-verification build tuning (Windows / sccache)

The build profile is tuned so the agent inner loop is cheap while the orchestrator's full pass stays correct. The general flow is **`cargo clippy` + narrow `cargo nextest`** for sub-agents, **full build + test in orchestrator verification**.

- **Debuginfo lever**: `~/.cargo/config.toml` sets `[profile.test] debug = "line-tables-only"`. Config-file profiles OVERRIDE `Cargo.toml` profiles, so this is the layer that actually takes effect on this machine (a `debug` set in any `Cargo.toml` is shadowed — confirmed: a probe crate's `Cargo.toml debug = 0` still built at `-C debuginfo=2`). Test binaries keep `file:line` panic backtraces but skip full-PDB generation — the single biggest codegen + link cost on MSVC. `[profile.dev]` stays `debug = true`, so `cargo run` / interactive debugging of the binary is unaffected. (Corollary: `lumina/Cargo.toml`'s `[profile.dev.package."*"] opt-level = 2` is DEAD — the global config's `opt-level = 1` wins; effective dep opt-level is 1.)
- **Inner loop (sub-agents)**: a SINGLE `cargo clippy --manifest-path <crate>/Cargo.toml` covers BOTH typecheck and lint — clippy is a strict superset of `cargo check`. Do NOT run `cargo check` then `cargo clippy` against the same target dir: they use different rustc wrappers, so artifacts have different fingerprints and alternating recompiles the whole crate. For a narrow test run use `cargo nextest run --manifest-path lumina/Cargo.toml --profile quick -E 'test(<area>)'` (the root manifest is the workspace, so nextest runs across all members) — the committed `quick` profile (`lumina/.config/nextest.toml`) excludes the two e2e binaries that spawn a real nested `claude` (`pty_e2e`, `conpty_minimal_repro`). Keep incremental ON (the config default) for this loop.
- **Orchestrator full verification**: prefix the full build/test pass with `CARGO_INCREMENTAL=0` (PowerShell: `$env:CARGO_INCREMENTAL=0; cargo …`). A throwaway full build never reuses incremental state, and turning incremental off lets the `sccache` rustc-wrapper cache the (now non-incremental) units — sccache cannot cache incremental compilations. tomlctl + all crates.io deps then cache across clean / branch-switch builds; lumina's own crate stays sccache-uncacheable regardless (its `sqlx::migrate!` / `static-serve` file-embedding macros trip sccache's missing-input guard), so the win there is the dep graph, not the lib. The `quick`/narrow filters are sub-agent affordances only — full verification keeps running everything (`cargo nextest … --profile ci`).

## Build & test

> In a flow, these are run by the orchestrator's `verification` step, not by each sub-agent — see **Build discipline in multi-agent flows** above. Sub-agents prefer `cargo check`/`cargo clippy` sparingly.

- `cargo build --manifest-path tomlctl/Cargo.toml` — build tomlctl
- `cargo install --path tomlctl` — install the `tomlctl` binary onto your PATH (run once per clone; rerun when the tomlctl binary version bumps)
- `cargo test --manifest-path tomlctl/Cargo.toml` — run tomlctl tests; this gates carrier↔CLI flag drift (the `command_lint` test) and asserts every skeletonised carrier still invokes its required `flow-contract-*` skills (the `carrier_invokes_required_skills` test). The `blocks verify-skills` engine / `verify_skills_clean` test is also run but is currently DORMANT post-wave-2: no manifest block retains both a `skill=` field and an embedded carrier copy, so the engine checks zero blocks and the test passes vacuously — it reactivates only if a future wave re-embeds an externalised block. All run via `cargo test` in CI, not via the pre-commit hook.
- `cargo clippy --manifest-path tomlctl/Cargo.toml --all-targets` — lint
- `cargo audit --file tomlctl/Cargo.lock` — RUSTSEC advisory check (install once via `cargo install cargo-audit`; run before releases and when updating dependencies). Run `cargo audit` weekly or before each release; the snapshot in CI/per-task acceptance is not a substitute for cadence.
- `bash scripts/verify-shared-blocks.sh` — verify shared-block parity for the manifest's sole remaining block, `forbidden-working-tree-ops`, across the two implement agents (run before committing changes to either agent; the pre-commit hook also runs this automatically when `core.hooksPath` is set per `## Developer setup`)

## lumina

`lumina/` is a standalone sibling Cargo workspace (the successor to `tomlctl`): a SQLite-canonical flow-tracking store fronted by an MCP server + axum JSON API + Vue SPA, with a git-export audit trail. It is built and tested independently of `tomlctl` (always pass `--manifest-path lumina/Cargo.toml`, which is the workspace root). The workspace has four members — `core` (`lumina-core`: domain/repo/db/export/import + migrations), `server` (`lumina-server`: the `lumina` + `pty_stub` bins, http/mcp/pty/assets), and `protocol`/`companion` (Step-1b stubs).

> In a flow, these are run by the orchestrator's `verification` step, not by each sub-agent — see **Build discipline in multi-agent flows** above. lumina is the heavier crate to compile, so this matters most here: sub-agents prefer `cargo check --workspace --manifest-path lumina/Cargo.toml` (or `cargo clippy`) sparingly and leave `cargo build`/`cargo test`/`cargo nextest` to verification.

- `cargo build --workspace --manifest-path lumina/Cargo.toml` — build the whole lumina workspace (use `-p lumina-server` for the server crate alone)
- `cargo test --workspace --manifest-path lumina/Cargo.toml` — run lumina tests, including the in-process end-to-end thread test (`lumina/server/tests/e2e.rs`: MCP write → DB rows → git-export snapshot → HTTP read, driven via `tower::ServiceExt::oneshot` and a direct export drain — no socket bind, no `sleep`)
- `cargo clippy --workspace --manifest-path lumina/Cargo.toml --all-targets` — lint
- `cargo install --path lumina/server --bin lumina` — install the `lumina` server binary onto your PATH; `--bin lumina` is REQUIRED because the `lumina-server` package ships two bins (`lumina` + `pty_stub`). Likewise a bare `cargo run` from the workspace root is now ambiguous — use `cargo run -p lumina-server` (or `cargo run -p lumina-server --bin lumina`).
- `cd lumina/server/web && bun ci && bun run build` — build the Vue SPA bundle into `lumina/server/web/dist/`; release builds bake this dir into the binary via `rust-embed` (debug builds serve it from the filesystem)
- `rg -c 'sqlx::query(_as|_scalar)?!\(' lumina/core/src lumina/server/src` — macro-eradication gate; must report ZERO matches. Part A converted every `query!`/`query_as!` compile-time macro to a RUNTIME `sqlx::query*` call behind the `DbClient`/`DbTx` seam, dropped the sqlx `macros` feature, and DELETED `lumina/.sqlx/` + `SQLX_OFFLINE`, so there is no offline cache to keep in sync and no `cargo sqlx prepare` step. (The `migrate` feature is kept for the compile-time `sqlx::migrate!("./migrations")` in `db.rs`.)
- `cargo audit --file lumina/Cargo.lock` — RUSTSEC advisory check (mirrors the tomlctl cadence: run weekly / before releases). The lockfile stays at the workspace root.

The dev DB `lumina/lumina.db` is gitignored and recreated on demand by `db::init` (the startup path, which also runs the embedded migrations) or `sqlx migrate run`; `lumina import-flow <slug>` ingests one existing `.claude/flows/<slug>/` flow into the store.

### MCP tool surface & the agent skill

The MCP server (`lumina/src/mcp/mod.rs`, rmcp 1.7 Streamable-HTTP, mounted at `/mcp`) exposes a domain-shaped surface of 74 tools (the count-invariant test in `mcp/mod.rs` asserts exactly 74) that an agent drives to define and execute work. The Round-1 baseline was 39: read tools (`list_work_items`, `get_work_item`, `get_tree`, `get_sprint_view`), definition tools (`create_work_item`, `update_work_item`, `move_work_item`, `delete_work_item`, `set_story_plan`, `set_task_spec`, `create_context_block`, `link_context_block`), and execution tools (`record_task_activity`, `transition_status`, `add_finding`, `update_finding`, `resolve_finding`). The migration-0003 planning/decision pass added the following tool families: relevance/effort/complexity/closure-gate setters (`set_relevance` on epic/focus/story, `set_effort` + `set_complexity` on tasks, `set_closure_gate` on stories); acceptance-criteria CRUD (`add_acceptance_criterion`, `check_acceptance_criterion`, `uncheck_acceptance_criterion`, `remove_acceptance_criterion` — a check appends a `verification` activity and the per-story `closure_gate=hard` then gates task→done while any criterion is unchecked); first-class research notes (`add_research_note`, `update_research_note` for confidence/state/rationale/lens, `supersede_research_note`); open questions with option→branch resolution (`add_open_question` story-scoped, `add_question_option`, `block_task_on_question`, `set_enabling_option`, `resolve_open_question` — picking an option unblocks that branch's tasks and cancels the other branches' exclusive tasks, emitting exactly one event); finding/research supersession (`supersede_finding` mirrors `supersede_research_note`); and origin (provenance) stamping threaded through `create_work_item`/`add_finding`/`record_task_activity` (plus `confidence` on `add_finding`/`update_finding`). The migration-0004 project↔repo-links pass added five further tools (`add_repo_link`, `remove_repo_link`, `set_primary_repo`, `list_repo_links`, `set_finding_repo`): a project work-item may carry one or more linked GitHub repos identified by a bare `<owner>/<name>` slug (both segments case-folded to lowercase on store, `*.git` suffix rejected), with at-most-one marked primary via a partial UNIQUE index on `repo_links(project_id) WHERE is_primary = 1`; findings may bind to a non-primary linked repo via the new optional `findings.repo_id` FK column (added by `lumina/migrations/0004_repo_links.sql` as a forward-only nullable column, since SQLite's `ALTER TABLE ADD COLUMN … REFERENCES` only accepts a NULL default) and otherwise resolve implicitly to the project's primary; correspondingly the `set_task_spec` tool's `files_touched` JSON array is widened beyond strict `string[]` so each entry may be either a bare path string (legacy form, resolves to the primary) or a `{repo: "<owner>/<name>", path: "<repo-relative path>"}` object whose `repo` slug must reference a `repo_links` row on the task's project ancestor (`mcp.rs` validates this against `repo::find_project_ancestor` + `list_repo_links`, rejecting unknown slugs as `invalid_params`). The slug shape is GitHub-only by deliberate choice (user-accepted trade-off); a future move to GitLab or self-hosted hosts would require a host-qualifying migration to widen the slug column, since the bare `<owner>/<name>` form carries no host discriminator. Each tool maps to exactly one `repo::*` mutation (preserving the +1 work_items / +1 events single-mutation-path invariant) or composes existing reads; every write records one `events` outbox row in the same transaction, which the git-export drain later materialises. The `attributes` (kind-specific JSON, e.g. a story's `problem_statement`/`research_notes`/`execution_strategy` via `set_story_plan`) and per-item `activity` log (via `record_task_activity`, migration 0002), together with the migration-0003 `work_items` columns (`relevance`/`effort`/`complexity`/`origin`/`closure_gate`) and the four FK child tables (`acceptance_criteria`, `research_notes`, `open_questions`, `question_options`, each folded into `WorkItemDetail`), plus the migration-0004 `repo_links` side table (folded into `WorkItemDetail` only for project-kind items) and `findings.repo_id`, flow end-to-end DB → git-export snapshot → HTTP detail (`GET /api/work-items/{id}`), as exercised by the deterministic in-process threads in `lumina/tests/e2e.rs`.

The migration-0005 round-2 planning pass added the following tool families: risks CRUD (`add_risk`, `update_risk`, `supersede_risk`, `remove_risk` — severity ∈ low|medium|high|critical, CHECK-constrained at the DB layer because severity gates sprint composition); rejected-alternatives CRUD (`add_rejected_alternative`, `update_rejected_alternative`, `supersede_rejected_alternative`, `remove_rejected_alternative` — confidence is free TEXT mirroring research_notes); first-class task graph (`block_task_on_task`, `unblock_task_from_task`, `list_task_dependencies`, `compute_task_batches` — the latter runs Kahn's-algorithm phase batches over a story's task subtree, returning `AppError::Cycle{edges}` on a detected cycle, surfaced at the MCP layer as `invalid_params` with the offending edges in the message); story readiness (`get_story_readiness` returns `{problem_statement_set, accepted_research_count, unresolved_questions, has_approach, has_acceptance_criteria_on_all_tasks, ready_for_decomposition, next_recommended_action}` and is the read consumed by the `/lumina:next-block` advisor and `/lumina:plan-story` chained runner); task-kind discriminator (`set_task_kind` stamps `work_items.task_kind ∈ foundation | vertical-slice | pattern-replacement | polish`, kebab-case to match the SQL CHECK); and the widened `set_story_plan` (now accepts `not_doing: Option<String>` and `verification_commands: Option<{build, test, lint, smoke}>` JSON-merge fields composing on `set_work_item_attributes`).

The migration-0006 round-3 dispatch-grade pass added a typed dispatch tier and a story-level dispatch-plan composer: `set_task_tier` writes the new `work_items.tier` column (CHECK-enforced `lite|deep|NULL`); `get_task_dispatch_plan` returns `Vec<Vec<BatchEntry>>` composing `compute_task_batches` + per-task spec reads + `compute_tier(effort, complexity, files_touched_count, has_cross_repo)` per row (rule: Deep if complexity=high OR effort=L OR files>3 OR cross-repo; else Lite — single source of truth in `repo::compute_tier`, documented in CONVENTIONS.md §k of the lumina-story-blocks plugin); `SetTaskSpecParams.dispatch` was renamed to `tier: Option<Tier>` (typed), forward-only break — legacy callers passing `dispatch:` have the field silently dropped at deserialise. Note the deliberate severity vocab split: `Severity::{Critical, Major, Minor, Suggestion}` (review-finding categorisation; already typed on `findings.severity` at the MCP-param surface) and `RiskSeverity::{Low, Medium, High, Critical}` (risk severity; CHECK-enforced on `risks.severity` since migration 0005) are NOT unified — they describe different concerns.

The migration-0011 Part-B pass added the findings-queue / runs / sprints / finding-decisions batch+query+domain tooling — nine new tools (B18 batch-write: `add_findings`, `create_work_items`, `batch_update_findings`; B21 query: `query_findings`, `get_story_finding_queue`; B24 run/sprint/triage domain: `create_run`, `create_sprint`, `add_tasks_to_sprint`, `record_finding_decision`) plus their HTTP mirrors. The three batch-write tools deliberately deviate from the per-call `+1 work_items / +1 events` invariant, recording one coarse, export-inert event per batch (bulk-created/spawned rows are not git-exported individually — the accepted D8/R-B4 trade-off); see `lumina/CLAUDE.md` § MCP tool surface for the full per-tool detail.

The migration-0013 team-execution pass added the atomic work-queue that lets a team of agents (via `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) execute a pre-planned task graph concurrently against the durable store — six new tools (`claim_next_task`, `release_task`, `renew_lease`, `complete_task` write; `get_sprint_quiescence`, `list_open_questions_for_sprint` read) plus their HTTP mirrors, taking the surface from 67 to 73. The migration adds four nullable `work_items` columns (`assignee` / `lease_expires_at` / `lane ∈ implement|review` / `reviews_work_item_id`). `claim_next_task` is one `BEGIN IMMEDIATE` txn (lazy lease-reclaim → first-ready candidate select → lease) and is the race-free primitive the agent-teams shared list cannot provide; intra-sprint file-overlap is **advisory only** (an out-of-txn post-commit read, never a gate — per [ADR-0002](docs/adr/0002-sprint-execution-architecture.md)). `complete_task` cascades a `lane='review'` task back-linked via `reviews_work_item_id`, and reviewers spawn rework through the existing findings→`record_finding_decision(spawn_task)` path. See `lumina/CLAUDE.md` § MCP tool surface for the full per-tool detail.

The migration-0015 session-corpus pass ([ADR-0004](docs/adr/0004-harness-session-corpus.md) layer 2) landed the lossless transcript-ingest substrate and added one read-only MCP tool — `get_session_context` — taking the surface from 73 to 74 (the count-invariant test in `mcp/mod.rs` then asserted 74). It captures every spawned/ingested `claude` session's JSONL verbatim into a new `session_records` corpus table, harvests sprint/agent/task correlation hints onto `pty_sessions`, exposes an unauthenticated loopback-only `POST /api/sessions/ingest` hook endpoint, and ships a `lumina init-hooks` CLI to wire that hook into a project's `.claude/settings.json`. See `lumina/CLAUDE.md` § Session corpus for the full detail (table shape, drop-at-ingest asymmetry, lossless-at-rest / redact-on-egress-deferred posture).

The migration-0016 sprint-lifecycle / worktree-ownership pass ([ADR-0005](docs/adr/0005-sprint-lifecycle-worktree-ownership.md), building on [ADR-0003](docs/adr/0003-commit-checkpoint-provenance.md)) added nine MCP tools — taking the surface from 74 to 83 (a later non-migration change — `lane` as a first-class task field, adding the `set_task_lane` tool — raised it to 84, so the count-invariant test in `mcp/mod.rs` now asserts 84; next migration = 0017). The eight-tool worktree/checkpoint/commit family is `create_worktree`, `get_worktree`, `list_worktrees`, `record_worktree_merge`, `record_worktree_rejection`, `set_task_checkpoint`, `record_task_commits`, `list_task_commits`; the ninth is the sprint-lifecycle setter `set_sprint_status`. A worktree is owned by EXACTLY ONE sprint (`worktrees.owning_sprint_id` UNIQUE FK) and its status is WHOLLY DERIVED from that owner (no `worktrees.status` column — `effective_status` is JOIN-derived); follow-up sprints TARGET a worktree (sharing `sprints.worktree_id`) but never own it, and merge audit is record-only (`merged_at` / `merge_ref` / `outcome`). lumina is RECORD-ONLY here: it never shells to git. The `SprintStatus` lifecycle is `{ Draft, Ready, Active, Review, Done, Cancelled }` (repo-enforced over `sprints.status`; `create_sprint` defaults `draft`); `set_sprint_status` rejects a terminal `review→done|cancelled` flip on a worktree-OWNING sprint (use `record_worktree_merge` / `record_worktree_rejection` instead). The claim guard is stricter: a task is claimable ⟺ its sprint is `active` AND the sprint is not frozen by an in-progress checkpoint task (`work_items.checkpoint=1` is a runtime freeze over the whole sprint, NOT a task→task dep). `record_task_commits` gives explicit task-id-list commit provenance (idempotent via `UNIQUE(commit_sha, task_id)`), recording one inert `worktree` event aggregate that is never git-exported. See `lumina/CLAUDE.md` § MCP tool surface for the full per-tool detail.

The companion agent-facing usage guide for this tool surface lives in the plugin's model-discoverable skill at `claude/plugins/lumina-story-blocks/skills/mcp/SKILL.md`. The same write surface is mirrored at HTTP under `/api` (every route delegates to the same `repo::*` mutation the matching MCP tool calls) — see `lumina/CLAUDE.md` § HTTP routes for the full route catalogue.

### Runtime queries (no offline cache)

Part A eradicated the sqlx compile-time `query!`/`query_as!` macros: every query is now a RUNTIME `sqlx::query*` call routed through the `DbClient`/`DbTx` seam in `lumina/src/db.rs` (`AnyPool::begin()` issues `BEGIN IMMEDIATE` for the write path). The sqlx `macros` feature was dropped and `lumina/.sqlx/`, `SQLX_OFFLINE`, and the `[profile.dev.package.sqlx-macros]` build tuning were DELETED — so there is NO offline query cache, no `cargo sqlx prepare`/`--check` gate, and nothing to regenerate. The replacement check is the macro-eradication gate: `rg -c 'sqlx::query(_as|_scalar)?!\(' lumina/core/src lumina/server/src` must report ZERO matches (a stray bang-macro reintroduces the compile-time DB dependency the seam removed). The `migrate` feature is retained for the compile-time `sqlx::migrate!("./migrations")` in `db.rs`. Tests assert DB state via the same runtime `sqlx::query_scalar(...)` string API.

## Testing discipline

This repository ships three composable packages for standing up test infrastructure, enforcing test-first discipline, and authoring well-structured tests on demand. Use `/test-bootstrap` once per project, `/tdd` once per feature, and let the model invoke `test-author` automatically when test-writing is needed.

### `/test-bootstrap`

Run once per project to install a modern testing stack. The command runs in 5 phases: (1) **Project Profile detection** walks manifests, infers project type/scale/CI provider, ingests CLAUDE.md hints, AND surveys public symbols for showcase-bundle binding (a ranked list of `slot:happy` / `slot:error` / `slot:tempdir` / `slot:mock` / `slot:property` candidates); (2) **Parallel research-agent fan-out** dispatches 4 agents (Test runner / Coverage / Mutation+Property / CI integration) that use Context7 + WebSearch to surface current best-practice tooling for the detected profile; (3) **Synthesis** produces 2-3 cohesive stack candidates ("Mainstream/safe", "Cutting-edge/active", "Minimal") presented via `AskUserQuestion`; (4) **Scaffolding** writes config, smoke test, showcase tests demonstrating good practice (AAA / parameterised / error-path / per-test tempdir fixture / mock-at-smallest-boundary / optional property-based — each slot binds to a user-code candidate via the *characterization-test* pattern when one fits, falling back to a synthetic SUT only when no project symbol fits the slot; opt out with `--no-showcase`), CI workflow, and `.gitignore` patterns verbatim from the chosen stack's templates; (5) **Marker-block writes** record the chosen stack in target CLAUDE.md and `.gitignore` between idempotent `<!-- TEST-BOOTSTRAP:STACK -->` markers so re-runs detect prior state and prompt rather than overwrite. Pass `--with-mutation` to additionally scaffold opt-in mutation testing on a separate `workflow_dispatch` / weekly schedule (mutation runs are 10×–100× normal CI time and never gate every push). Recommendations are produced fresh per invocation rather than read from static reference docs — two runs months apart on the same project may surface different stacks as ecosystems evolve, and the marker block records what was chosen + when.

### `/tdd`

Run once per feature INSIDE an existing `/plan-new` flow. Prerequisite: `/test-bootstrap` has been run on the target project (or the parent plan's `## Verification Commands` block declares a `test:` command). `/tdd` loops RED → GREEN → REFACTOR cycles. RED captures a SHA256 fingerprint over the project's test files (post-commit, from `git ls-tree`) and invokes the `test-author` skill to write a failing test. GREEN dispatches `/implement --flow <parent-slug>-tdd-<NNN>` with a one-task mini-plan; on return, the test-file fingerprint MUST equal RED's value (anti-cheat: no test mutation). REFACTOR runs the coverage tool and may loop GREEN if changed-line coverage <90%. Each cycle gets a transient sub-flow at `.claude/flows/<parent-slug>-tdd-<NNN>/` whose `task-completion` and `verification` entries are copied up into the parent flow's execution-record on completion (with `task_ref` prefixed `tdd-cycle-<NNN>-…` and `E`-prefix IDs re-minted to avoid parent-namespace collisions). A per-parent-flow `.tdd.lock` prevents concurrent /tdd invocations from racing on cycle-NNN allocation.

### `test-author` skill

Model-discoverable polyglot skill. Activates automatically when the user asks for tests ("write tests for X", "add coverage for Y", "test this function", "generate test cases", "scaffold tests"). Composed by `/tdd`'s RED phase; usable standalone. Framework detection follows a 5-step precedence: (1) target project's CLAUDE.md `<!-- TEST-BOOTSTRAP:STACK -->` marker block (highest priority — set by a prior `/test-bootstrap` run); (2) parent flow's plan-file `## Verification Commands` block; (3) repo manifest walk (Cargo.toml → pyproject/requirements → package.json → go.mod); (4) closest manifest by directory (monorepo tiebreaker); (5) halt with `"No test framework detectable. Run /test-bootstrap first."` Per-language output idioms (Rust / Python / TypeScript / Go) are documented inline in `claude/skills/test-author/SKILL.md` — there are no separate per-language reference docs to maintain.

## Flow registry & plansDirectory

The `plansDirectory` setting in `.claude/settings.json` controls where plan files are stored. It accepts either a string or an array of strings (e.g. `["docs/plans/", ".claude/plans/"]`). Note: the upstream Claude Code settings schema (`https://json.schemastore.org/claude-code-settings.json`) may define `plansDirectory` as string-only — if so, `tomlctl` stores the array under a namespaced key (`tomlctl.plansDirectories`) and reads both for back-compat. Use `tomlctl json get .claude/settings.json plansDirectory` to inspect the current value.

### Adopting the flow registry

When switching an existing repo to the `tomlctl`-backed flow registry (`.claude/active-flow.toml`), perform this one-time migration:

> **WARNING: this procedure permanently destroys flow history.** Step 1 (`rm -rf .claude/flows/`) deletes every per-flow directory including `execution-record.toml`, `review-ledger.toml`, `optimise-findings.toml`, and `plan-review-findings.toml`. There is no `tomlctl flow migrate` command yet — the planned migration tool is out of scope for this initial overhaul. If you have in-flight flows whose history matters, back up `.claude/flows/` (e.g. `cp -r .claude/flows/ .claude/flows.bak/`) before running step 1, or skip the migration entirely until a migrate command lands.

1. Clear the old per-flow state directories: `rm -rf .claude/flows/`
2. Delete the legacy single-line active-flow file: `rm -f .claude/active-flow`
3. For each flow that should be recreated, run:
   ```bash
   tomlctl flow init --slug <slug> --plan <path/to/plan.md>
   ```
   This seeds `context.toml` + `execution-record.toml` under `.claude/flows/<slug>/` and registers the flow in `.claude/active-flow.toml`.

After migration, all flow commands (`tomlctl flow list`, `tomlctl flow resolve`, etc.) read from `.claude/active-flow.toml` exclusively; the legacy `.claude/active-flow` file is ignored.

## Integrity sidecar (.sha256) — scope

`tomlctl` writes a `<file>.sha256` sidecar on every `tomlctl items apply` / `tomlctl set` / `tomlctl flow init` write (suppress with `--no-write-integrity`). The sidecar exists to detect **accidental corruption** — a torn write, a buggy tool that mangles the TOML, or out-of-band manual edits that break the schema. `tomlctl <op> --verify-integrity` errors on digest mismatch and never auto-repairs.

**The sidecar is NOT a tamper-evident seal.** An attacker who can write to `.claude/` can update both the TOML and the sidecar atomically, and the digest check will pass. If you need adversarial integrity (signed artefacts, append-only logs, untrusted-collaborator defence), the sidecar is not sufficient — review the file's git history, sign commits, and treat ledger writes the same way you'd treat any other CI script that runs unsandboxed.
