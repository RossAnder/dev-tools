# engine-settle-fit

## Answer

- **Running a settle task: yes, with one shape constraint.** The Workflow refuses a task with empty `files`, and the engine drops one before launch. So a settle task has to claim a proposal file, for example `docs/flows/<slug>/notes/settle/<n>.md`. It cannot use only its run note. Everything else holds: `plan check` requires an `accept` with a `check` (a `test -s`/`grep -q` on the proposal file with `writes_build = false` meets that); zero premises record cleanly; an empty `gates` is only a warning and the gate step skips; the milestone commit stages the proposal file. The worker procedure assumes a code edit only in wording: the compile check is conditional ("after a non-trivial code edit"), and "what changed, file by file" fits a doc. The real code assumption is in the **commit**. A milestone whose rows leave no file that `git status` prints reaches `git commit -m … --` with no paths, which fails with "nothing to commit" (rc 1). The engine treats any failed commit as fatal, so the proposal file is required, not optional.
- **Minting fix tasks at drain: the verbs allow it, the procedure does not say it.** `tasks add-many` accepts any declared checkpoint (`reject_undeclared_checkpoint`), and an approved plan stays approved or running when rows are added (`plan/stage.rs` `assess` keys on approvals and row status only). But the drain reads a note only for a non-`done` task, or one with deviations or a handover. A settle task that finishes `done` with a proposal is never read. The replan table has no "proposal" input. New tasks are minted only "in the same milestone", so "this gate and this commit". The return schema has no proposal field. A drain step that reads settle notes and mints into the following milestone is new procedure.
- **One user gate between two milestones: not as decided.** `[[milestones]]` has no pause field (`MilestoneSpec` = id, gates, elaboration, defer_reason). After a commit the engine goes straight on to the next milestone unless something in the flow is parked or `--milestone` was given. A parked row does stop it. The next invocation then re-asks every parked row of the milestone about to run, four per `AskUserQuestion`, with "as the note proposes / another way / drop / leave parked". That is close to the decided gate. But a row left parked means "the milestone runs its disjoint work and cannot gate". An unanswered proposal parked in the fix milestone would therefore hold every other fix in that milestone uncommitted, against "an unanswered proposal leaves its finding open" (`docs/ideas/v2-pipeline.md:186`). A deferred fix milestone is no alternative. It stops the engine only while it holds a row, because the pick skips a checkpoint with no non-`done` row and `plan stage` reads `done` once every row is done.
- **Adjacent conflict, one line:** the decision "a fix worker that returns needs-a-decision … goes up a tier" (`v2-pipeline.md:195`) contradicts the engine's "Never up a tier" (`SKILL.md:20`, `drain.md:123`). That belongs to the plan's burden-of-proof milestone. It is not this lens's to settle.
