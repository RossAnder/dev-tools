## Answer

- **What to stub.** Each script reads only these free globals. review-v2.js uses `args` (34), `log` (29), `agent` (118, 220, 226, 232, 247, 272), `parallel` (143, 224, 257, 314), `pipeline` (319) and `phase` (142, 318). plan-v2-review.js uses `args` (33), `log` (31), `agent` (191, 213, 240, 277), `parallel` (378), `workflow` (326) and `phase` (224, 298, 322, 411). Neither touches `budget`, `Date`, `Math.random`, `require` or `process` (an rg over both files found none). `phase` and `log` can be no-op recorders. `agent` is a function that takes `(prompt, opts)` and returns a canned answer. Tests key the answer on `opts.agentType` or `opts.label`, and pull the ids out of the prompt's `findings:` line.
- **How to load a script.** Strip `export ` from `export const meta`, then build `new AsyncFunction('args','agent','parallel','pipeline','phase','log','workflow', body)`. A direct import fails. Run under each runner from the repo, `import()` of each script printed `SyntaxError: Illegal return statement` under node, and bun printed `AggregateError: 4 errors building ...review-v2.js` and `7 errors building ...plan-v2-review.js`.
- **Runtimes here.** `/usr/bin/node` is v26.13.0, `/usr/bin/bun` is 1.4.4, and deno is also installed. A prototype written against the `node:test` and `node:assert/strict` API was run as `node --test harness.test.mjs` and as `bun test ./harness.test.mjs`. Both runners gave `2 pass, 0 fail`, so one file serves either runner. `node --test <dir>` and `bun test ./<dir>` both find the file when given its directory.
- **Windows.** This machine cannot see it. Indirect evidence suggests node is present there: docs/ideas/plan-v2-probes.md:93 says "Transcripts from this Windows machine show thousands of python and node snippets". bun is present only if lumina's SPA is built there (lumina/CLAUDE.md:17, lumina/web/CLAUDE.md:15), and the repo does not record whether it is. **To settle it:** run `node --version; bun --version` in Git Bash on that machine, which is the shell the hook runs under.
- **How the hook or the suite would run it.** Either route works. The planner has to choose between two costs:
  - *A hook line.* For example `gate node --test "$ROOT/claude/workflows/tests/"`, under the same `^claude/workflows/.*\.js$` condition the dispatch gate already uses (.githooks/pre-commit:54-57). The cost is that the orchestrator's full `cargo nextest` pass never runs it.
  - *A Rust test under `cli::dispatch::tests` that runs `node --test`.* The existing hook gate and the full suite would both pick it up. The cost is that the crate suite and the `verification` agent then need node, and the test needs a rule for a machine without node: skip quietly, or fail.

## Findings

- **Library/API or file**: claude/workflows/review-v2.js:76,144,325 and claude/workflows/plan-v2-review.js:86 — the top-level `return` statements
- **Source**: `node --input-type=module -e "import('…/review-v2.js')"` → `SyntaxError: Illegal return statement`. Same result for plan-v2-review.js. bun gives `AggregateError: N errors building`.
- **Evidence-grade**: high
- **Finding**: neither script can be imported as a module. The harness has to read the source, rewrite `export const meta` to `const meta`, and wrap the rest in an AsyncFunction whose parameters are the stubbed globals.
- **Details**: lint.rs:1035 already records that a script's top-level `return` fails `node --check`. Once wrapped, a script's `return index(...)` becomes the value the AsyncFunction resolves to. Test fixtures can then assert directly on `agents`, `errors`, `escalations`, `unverified` and `waves`. The anchored regex `/^export const meta\b/m` also matches a CRLF checkout, and JS normalises CRLF to LF inside template literals, so the prompts tests match against are the same on Windows.
- **Counter**: if the Workflow runtime exposed a module form that let these scripts be imported, the loader would be unnecessary. The workflow-authoring reference documents only top-level script bodies.
- **Impact on plan / report**: the harness needs a loader (about 5 lines) as well as the stubs. The loader rewrites `export`, so if a script ever exports anything besides `meta`, the loader must change too.

- **Library/API or file**: claude/workflows/review-v2.js:143-144,224,257,314,319,325 and plan-v2-review.js:95-103,326,378 — the stubs for `parallel`, `pipeline`, `workflow` and `agent`
- **Source**: the workflow-authoring skill's hook reference, read 2026-11-11: `parallel` resolves a thunk that throws to `null` and never rejects. `pipeline` passes `(prevResult, originalItem, index)` to each stage, and a stage that throws turns that item into `null`. `agent` returns `null` when an agent is skipped or dies. `workflow` throws on an unknown name.
- **Evidence-grade**: high
- **Finding**: stubs must reproduce these failure semantics, not just a working happy path. The scripts' error-path branches only run when the stubs return `null` this way.
- **Details**: review-v2.js:144 and 325 fill in `null` rows (`'unit did not settle'`, `status: 'error'`). routeCell at review-v2.js:277 needs `pipeline` to pass `(ret, cell)`. plan-v2-review.js wraps every call in `caught()` (95-101), so a throwing `agent` or `workflow` must reach that wrapper. The prototype's stubs are each one line. `settle` wraps a call in try/catch and returns `null` on error. `parallel = thunks => Promise.all(thunks.map(settle))`. `pipeline` chains the stages per item inside `settle`. `workflow` dispatches to a map of child functions and throws for any name not in it. The `workflow` stub can run the loaded review-v2.js with the same stubs. That gives an end-to-end check of plan-v2-review's agent total (review-v2.js returns `agents`, which plan-v2-review.js:346-347 adds).
- **Counter**: if the real runtime's `pipeline` passed different arguments to later stages, or rejected on a throw, the stubs would test behaviour that never ships. A real run's journal.jsonl would show it.
- **Impact on plan / report**: the task spec should state the stub semantics, not just the stub names.
