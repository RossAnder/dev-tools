Verdict: no restructure. Each half already has one owner: the `Handover` record path in `tomlctl/src/plan/` for v2, and `flow-contract-plan-output-format` for v1, which review cells already read through the `FORMAT CONTRACT` fence. The work extends both owners and removes the restatements around them. Four forced edits inside those owners are listed below.

# Structure challenge: human-only handovers

## Why the present structure holds

**v2: the approval gate already comes from `plan check`, so a new finding class is enough.**
`plan approve` refuses on any ERROR finding from `check::findings` (`tomlctl/src/plan/approve.rs:186`, `approve.rs:282-295`). Handover findings already reach that list (`tomlctl/src/plan/check.rs:70-74`). A finding raised for a missing "why only a person", "when" or "done when" therefore blocks approval with no change to `approve.rs`. That meets the first future-state bullet through the existing seam.
Refuted if: `refuse_check_errors` filters findings by class rather than by severity. Today it filters by severity, apart from the `plan/brief-changed` exemption under `--amend`.

**v1: one owner exists, and review cells already treat it as the only source.**
`plan-new.md:119` calls `flow-contract-plan-output-format` "the single source for the output shape". The `format-contract` check sends the plan-family cells to that skill's `SKILL.md` and nowhere else (`claude/skills/review-v2-lenses/checks/format-contract.md:17`, `:36-37`). `plan-structure.md:30` says that fence "is the only source". A new `flow-contract-handover` skill would be a second owner that no fence points at. The rule therefore belongs in the existing owner, and the other sites should point at it rather than restate it.
Refuted if: some plan consumer has to read the rule but cannot load `flow-contract-plan-output-format`. The v2 engine is the candidate, and its handover prose would sit in `plan-v2-engine/references/write-and-prove.md`, next to the `plan.toml` shape it governs.

## Edits the change forces inside the present structure

1. **The `[[handover]]` shape models the wrong thing.** `Handover` is `{id, command, source_task, done}` (`tomlctl/src/plan/schema.rs:299-304`). The CLI documents `command` as "The command to run" (`tomlctl/src/cli/types/plan.rs:169`), and `plan-store.md:136` documents it as "A command a person must run". A runnable command is exactly the kind of step the intent says an agent should perform. The future state needs to record what to do, when, how to tell it is done, and why only a person can do it. That means new keys, or renamed ones, through `handover_from_toml` / `handover_to_toml` (`schema.rs:746-778`), the required-key and flag tests (`schema.rs:1025-1026`, `:1043`), the fixture (`schema.rs:908`), and the arg structs (`cli/types/plan.rs:166-189`).
   Refuted if: `command` can hold free prose and the three new facts can be checked inside one string. They cannot be: `check.rs` would have to parse prose.

2. **Adding keys without a version bump loses data silently.** The store drops unknown keys on every write (`schema.rs:13-14`). The version guard refuses only a store newer than the binary (`schema.rs:353-361`), and `SCHEMA_VERSION` is `1` (`schema.rs:27`). An older installed `tomlctl` that rewrites a `plan.toml` holding the new handover keys would drop them with no error. The change therefore has two options: raise `SCHEMA_VERSION`, which makes an old binary refuse instead of drop, or accept the loss. The planner should record that choice as a decision.
   Refuted if: some write path keeps unknown keys. `to_toml` rebuilds the store from the struct, so none does.

3. **The handover verbs have no way to correct a record, and the only remedy misstates history.** `plan handover` has only `add` (flags) and `done` (`records.rs:334-364`). `plan decide` and `plan contract` take `--ndjson`, where a row with an `id` updates that record (`records.rs:149-171`, `:254-276`; `cli/types/plan.rs:155-160`). The remedy `plan stage` gives for a handover finding is "add a new one, then `plan handover done <old id>`" (`tomlctl/src/plan/stage.rs:25-26`, `:138`). `done` is the bit that means "the user performed it": `view.rs:215` renders it `[x]`, and `approve.rs:95` and `view.rs:424` drop it from what the user sees. A done handover is also exempt from checking (`check.rs:298-301`). Under the new required-field findings, every fix would leave a record falsely marked as performed by the user, and marking it done would also hide the defect. The handover write path should take the `--ndjson` add-or-update shape `plan contract` already uses, keeping `done` for real completion. The new classes need entries in `next_for` and its exhaustive test (`stage.rs:125-145`, `:300-326`).
   Refuted if: a planner can always get the fields right before the first `add`. The repair loop that `plan stage` drives exists because they often are not.

4. **`check.rs` returns one finding per handover.** `handover_finding` returns `Option<Finding>` and skips done records (`check.rs:300-311`), and the call site uses `filter_map` (`check.rs:71-73`). Several missing fields need a `Vec` and a `flat_map`, the shape `contract_findings` already has (`check.rs:270-296`, called at `:65-69`). Whether a done handover is still checked for the new fields is a decision for the planner, because `--amend` relies on done handovers being skipped (`check.rs:298-299`).

5. **The approval screen files handovers under things that stop the run.** `gate_report` chains milestone gate commands and undone handovers into one `stops` list that carries only `command` and `source_task` (`approve.rs:90-103`), and `plan-v2-engine/references/approve.md:60` presents it that way. A human-only step that happens after landing is not a run stop, and the screen has to show its why, when and done-when. That means a separate `handovers` key carrying all fields, plus the matching `open_items.undone_handovers` (`view.rs:421-426`) and the markdown line (`view.rs:212-224`), which today shows only the command and the task.

6. **v1: the rule has to go in the part of the contract the fence tells cells to read.** The After Merge template is the bracketed text at `flow-contract-plan-output-format/SKILL.md:206-211`. The fence's `read:` line covers only "the `**Format rules:**` block from line <r> to the end of the file" plus the Execution Policy template (`format-contract.md:36`). `**Format rules:**` starts at `SKILL.md:228`, after the template. A rule written only into the template is therefore invisible to review cells. Either add a Format-rules bullet, or widen `format-contract.md:36-37`. The template also lists agent-performable steps as its examples ("install or reinstall a binary, resync a plugin cache, … update a memory note, run a **predicted, unverified** success criterion by hand"), and those examples have to be inverted.

7. **Restatements that contradict the intent and must point at the owner.**
   - `plan-new.md:108` repeats the template's agent-performable examples word for word.
   - `implement.md:330` says After Merge items are "steps the user must take by hand" and reports them verbatim. It has nowhere to perform agent-doable steps. That fits once the plan puts those steps in tasks, so no new `/implement` phase is needed.
   - `plan-structure.md:34` treats a predicted criterion that After Merge does not schedule "by hand" as a defect. `:65` and `:70` count After Merge as a place where goals get verified.
   - `plan-risk.md:36`, `:57` and `:72` ask for After Merge lines to be added.
   These six sites are the "asking for more" behaviour the future state reverses.

8. **The v2 planner is never told to write handovers.** No file under `claude/skills/plan-v2-engine/` mentions `plan handover add`. Its one handover mention is the `stops` line at `approve.md:60`. The rule for when a step becomes a handover rather than a task belongs in `write-and-prove.md`, next to its contracts and decisions.

Side observation, outside this change's scope: `plan-store.md:137` says `source_task` is "Not checked against the rows", but `check.rs:300-311` raises `plan/handover-task-unknown`.

## Alternatives ruled out

- **A new `flow-contract-handover` skill owning the rule for v1 and v2.** No fence or carrier points at it. Plan-family cells read only `flow-contract-plan-output-format` (`format-contract.md:17`, `:36`). v2 enforcement is mechanical in `check.rs`, so v2 prose needs one paragraph in `write-and-prove.md`, not a shared contract. This adds a hop and no edit it would remove.
- **Making a human step a task row with a "human" executor.** Rows feed `tasks ready` and dispatch, so a human row would sit on the frontier or block it. `check.rs` would need new spec exemptions, and the approval screen would lose the separate list the future state wants.
- **A v1 parser for `## After Merge` in `tasks import-plan`.** No Rust code reads that section today: a search of `tomlctl/src` finds no "After Merge". Whether v1 needs mechanical enforcement or review-lens enforcement is enough is a decision for the planner about v1's remaining life, not a structural need. Either way it extends `import_plan` and `tasks check`, and nothing moves.
