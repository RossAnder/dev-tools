# /optimise — performance and efficiency research across five lenses

> Skim-readable orchestrator. Full contract bodies load on demand via skill invocations.

Researches code for performance and efficiency opportunities through five parallel lenses — Memory, Data Shape, Queries, Algorithm, Async — and persists findings to a TOML ledger keyed by stable `O{n}` IDs; re-runs dedupe, merge, escalate chronic items, and surface regressions. **Research-only**: it changes no code, and produces a findings report — run `/optimise-apply` afterward to implement. Targeted mode takes paths, directories, globs, feature names, or a `branch1..branch2` comparison as `$ARGUMENTS`; with no args, scope derives from recent git changes. Agents verify each claim against documentation and real benchmarks rather than assuming what is performant.

> **Effort**: Requires `max` — lower effort may reduce agent spawning and tool usage below what 5-agent coordination needs.

## Step 0: Pre-flight (flow resolution + doctor)

Invoke the `tomlctl` skill before the first `tomlctl` call: every flow-store read and write in this command goes through it, and its output options shape each report, so tomlctl output is never piped into `jq`, `python` or `head`.

Invoke the `flow-contract-flow-context` skill to load the flow-bootstrap envelope contract (input/output shapes, `envelope.ok` gating, `envelope.resolved.*` and `envelope.doctor.*` binding rules, no-flow fallback, doctor-fail handling, staleness reconciliation, and the mandatory bootstrap-summary console line).

Build the input envelope:

```bash
tomlctl flow envelope build \
  --command optimise \
  --branch "$(git branch --show-current)" \
  --worktree "$(git rev-parse --show-toplevel)" \
  --cwd "$(pwd)" \
  --staleness-threshold 7d
```

The block above is complete and copy-pasteable as-is — do NOT look up `--help`; `/optimise` lazily creates its findings artifact, so no `--require-artifact` flag is needed, and `--staleness-threshold 7d` is the default, passed explicitly for clarity. On detached HEAD, omit `--branch` so the envelope records `branch:null`. Add `--flow-override <slug>` when the user supplied `--flow`, and `--path-arg <p>` once per `$ARGUMENTS` path token. Dispatch `flow-bootstrap` via the Task tool with `subagent_type: "flow-bootstrap"` and the printed JSON as the prompt. Gate on `envelope.ok`; bind `slug`, `context_path`, `artifacts.*` (esp. `optimise_findings`), `doctor.ok`, and `resolved.stale` for downstream phases. Emit the bootstrap-summary line before any other action. When staleness fires for `/optimise`, invoke the `plan-update` skill with literal arg `reconcile` before continuing.

**User inputs.** Invoke the `flow-contract-user-inputs` skill and run its Step-0 sweep with `--ledger optimise` and `--by optimise`, selecting on the bound `slug`, or for a flow-less run on the `<scope>` Step 1 derives, so a flow-less sweep completes once Step 1 has resolved the ledger path. Fold each kept `note` into the Step 2 preamble as quoted user-supplied data. Each `request` this carrier can honour — `deferred`, `wontapply`, or reopening a `deferred` item, with the companion fields the ledger-schema skill requires taken from the record's text — becomes an op in the Interim checkpoint batch carrying `"expect": {"status": "<status read>"}`, and counts as a pending transition for that checkpoint's skip gate. Decline a request for `applied`, which only `/optimise-apply` writes once a change lands. Handle every acknowledged record before the Step 3 report.

## Step 1: Determine Scope and Load Prior Findings

**Reason thoroughly through scope analysis.** Resolve the in-scope file list from `$ARGUMENTS`: a branch comparison (`a..b`, `a...b`, `a vs b`) resolves via `git diff --name-only a...b` — always three-dot merge-base semantics regardless of input syntax, and any trailing text is a focus lens (`/optimise prod-hardening..master queries`); paths, directories, globs, or a feature/area name resolve directly (directories recurse; feature names via `Grep` + `Glob`); empty args or a bare focus lens derive from git — `git diff --name-only $(git merge-base HEAD master)..HEAD` on a feature branch, else `git diff --name-only HEAD~1`, plus unstaged `git diff --name-only`. Ask the user what to review if nothing is found. Classify every file by technology and area, and share the classification with all agents so each can skip files irrelevant to its lens.

**Before classifying**, read the project's `CLAUDE.md`. Its declared tech stack (runtime, frameworks, build tools, key libraries) is the **authoritative** classification source — it overrides inference from file extensions or imports. Also extract any `## Optimization Focus` section: those entries describe the project's optimisation *posture* — the lenses, scale constraints, and concerns the maintainer wants brought to the analysis. Pass both stack and posture to every agent verbatim, **with the explicit reminder that the posture is framing and not a closed checklist**: it shapes what to look for but does not cap the search, findings outside it are welcome, and a finding that only restates a posture bullet without independent evidence is weaker than one identifying something new.

**Small scope is not a shortcut.** When 3 or fewer files are in scope, still launch all five research agents — their value is five independent research threads (separate source lookups and lens-specific analysis), not divided file reads. Tell each agent the scope is small so it concentrates research depth on those specific code paths instead of fanning out.

Invoke the `flow-contract-ledger-schema` skill to load the canonical ledger schema (field set, category and disposition vocabularies, fail-soft rules, the `[[rollback_events]]` / `[[vet_events]]` event logs, the tomlctl parse-rewrite read/write contract, key-order convention, and the ID-assignment + dedup/regression rules). For `/optimise` the category vocabulary is `memory` | `serialization` | `query` | `algorithm` | `concurrency`, and the disposition vocabulary is `open` / `deferred` / `applied` / `wontapply` — there is no `verified-clean` counterpart. Resolve the ledger path from `envelope.resolved.artifacts.optimise_findings` when a flow resolved, else `.claude/optimise-findings/<scope>.toml` (derive `<scope>` per the flow-less slug rule in the flow-context skill: directory scope → `src-prime-api-endpoints.toml`, feature scope → `auth.toml`, git-derived → `{branch-name}.toml` or `recent.toml` on main). Load open items via `tomlctl items list <ledger> --status open --verify-integrity`; a missing file is a first run (`O`-numbering starts at `O1`) — do NOT hand-seed it, the first write auto-creates it with the schema skeleton. Load the `deferred` and `wontapply` items overlapping scope as well, with their `defer_trigger` or `wontapply_rationale`, for the agents' prior context: Step 3 already refuses to re-mint a match on those, but an agent that never saw them spends its budget rediscovering them.

**Lint baseline, once.** Run the project's declared lint (the `Build & test` section of its CLAUDE.md) one time here and keep the diagnostics touching in-scope files as a `LINT BASELINE` fence for every prompt; clippy's `perf` group already names the cheap wins, and a candidate it reports is not a finding. Five agents each running it serialise on one build lock. With no declared lint, embed `LINT BASELINE: not run — no lint command declared`.

Invoke the `backlog-capture` skill for the repo-scoped capture store's discipline, then load its live rows (`open` and `promoted`) alongside the ledger's (one `--area-prefix` per directory the scope spans; drop the flag only when the scope is the whole repo):

```bash
tomlctl backlog list --live --area-prefix <scope-dir>
```

Hand each returned row's `summary` and `context` to the lens agents as prior context: a row is a known repo-scoped issue plus how to work around it, so an agent tripping over the same thing does not spend the round rediscovering it. A `promoted` row is already claimed by the flow its `promoted_to` names: do not re-raise it as a new finding unless that flow is at `review` or `complete` or does not exist, and in that case point the user at `/backlog` to re-triage it.

Invoke the `flow-contract-ledger-disposition-sweep` skill to load the orphan-surfacing and deferred-reopen sweep contracts. Run both after the ledger loads and before agent dispatch. Orphan-surface read-only via `tomlctl items orphans <ledger>`; on an older binary predating that subcommand, fall back to a one-off `Glob` sweep over each item's `file` plus a `Grep` sweep over each item's `symbol`, leaving `depends_on` dangling-refs unchecked until `cargo install --path tomlctl`. Deferred-reopen is **a user-engagement gate — the autonomy directive does not apply** (every reopen passes through the per-item prompt; non-interactive invocations surface candidates only and never mutate the ledger).

## Step 1.5: Determine Focal Points

Before dispatch, determine the **project-specific optimisation focal points** — the runtime, framework, and compilation characteristics that should shape each lens — so agents probe for the right things rather than relying on generic heuristics. When `CLAUDE.md` declares both a clear tech stack AND an `## Optimization Focus` section, reason through the focal points directly; no agent is needed. Otherwise launch a single `subagent_type: "Explore"` agent (`thoroughness: "quick"`, output under 200 words) to sample 2-3 representative in-scope files and report language and framework versions, async runtime, serialization approach, database access layer, key libraries, and compilation/optimisation settings from project config (`PublishAot` / `PublishTrimmed` in a .csproj, `target` in tsconfig, `[profile.release]` in Cargo.toml, bundler config). Dispatch it one-shot — **never pass `name:`**: a named spawn becomes a teammate with no return channel, and the built-in `Explore` carries no teammate-delivery instruction, so its report is lost and you get only a "Teammate @x finished" notification. Treat that as a failed dispatch and re-dispatch unnamed rather than pumping it with `SendMessage`.

**Reason thoroughly** to combine the Explore findings (when launched), CLAUDE.md's stack and posture, and Step 1's classification into a **Focal Points Brief** — a compact set of per-lens directives naming the runtime/framework-specific patterns that lens should prioritise. Include each lens's slice in its Step-2 prompt. Focal points are **additive framing, not a narrowing**: agents still apply their full general lens and actively search outside the brief. Tell each agent explicitly that findings identifying new concerns outside the focal points are the highest-value output, and that findings which only cite the focal points without fresh evidence are weaker.

**Dev server, for frontend scope.** When any in-scope file classifies as frontend and the project's `.mcp.json` declares the `playwright` server, probe the dev URL the project documents (its CLAUDE.md, or the dev script in its manifest) and embed `DEV SERVER: <url>` in the preamble when it answers, `DEV SERVER: none` when it does not. The browser's network and console views serve Agents 1 and 2 (bundle, render and payload cost), so name it in those two lens prompts. Detect only: the run starts no server and no lens agent may. When nothing answers and the project documents a dev command, ask once whether the user will start it — a user-engagement gate the autonomy directive does not override, skipped on a non-interactive run — and re-probe on the reply.

## Step 2: Launch Parallel Research Agents

Launch all five agents in a single response message via the Agent tool, `subagent_type: "research-deep"` for every lens. All-deep is deliberate and there is no small-diff single-agent shortcut here: optimisation is judgement-heavy across the board (telling real bottlenecks from theoretical ones, spotting an idiomatic-looking pattern that is anti-optimal in this runtime, weighing fix cost against gain), and a misjudged optimise finding ships a regression or breaks an invariant, where a misjudged review finding is recoverable next round. Each agent receives the file list, classification, tech stack, focal points, and CLAUDE.md optimisation-focus excerpt as a **byte-identical literal preamble** at the top of its prompt (5-minute prompt-cache reuse — whitespace differences defeat it), with per-lens divergence below a clear divider; the `DEV SERVER` fence from Step 1.5 goes in the preamble when one was set. The agent loads the `research-methods` skill itself; do not restate its method in the prompt. The per-call prompt supplies the lens focus, the ledger path (also emitted as the first line of every lens prompt, on a line of its own at column 0, in the form `ledger: <repo-relative ledger path>` with the path only and no item ids; a flow-less ledger gets the line too and simply goes unattributed), the prior context including deferred and wontapply items, the `LINT BASELINE` fence, the finding-record fields, and the per-call cap (which overrides the agent's default ≤8).

Every lens here is scholarly-eligible when the win would be a novel algorithm, data structure or microarchitectural technique rather than a library-API swap; each lens below names its research domain. Every agent adapts to the technology at hand — not every lens applies to every file — and explains the *why*: what the current approach costs and what the better one gains, citing the doc or benchmark that established it.

Each finding is a structured record carrying the ledger-schema field set: `file`, `line` (`0` when no specific line applies), optional `symbol` (strongly recommended — line-drift resilience), `severity` (`critical` = measurable perf impact, `warning` = likely overhead or missed opportunity, `suggestion` = marginal gain or future consideration), `effort` (`trivial` | `small` | `medium`), `category`, `summary`, optional `description` (what the code does now, the specific change with a sketch of only the changed lines where it helps, and the tradeoffs/risks to verify after applying), and optional `evidence[]` in the ledger schema's entry format. Omit `id` / `first_flagged` / `rounds` / `status` — Step 3 assigns those. **Target 15 findings per agent, ceiling 20 — a ceiling and a target, never a quota.** Never include full file contents — reference by `file:line`.

**Agent 1 — Memory, Allocations and Runtime.** Allocation strategy, stack vs heap, pooling, boxing, object lifetime, closure captures, inlining, hot/cold path separation, and whether the code helps or hinders compiler optimisation (devirtualization, generic specialization, JIT/AOT codegen differences). On the frontend: reactive-object overhead, component-instance proliferation, bundle size, tree-shaking barriers, render-pipeline efficiency. Leaves async runtime and concurrency architecture to Agent 5. Research domain: compilers, codegen and memory management, plus the vendor microarchitecture manuals.

**Agent 2 — Data Shape and Wire Efficiency.** How data is shaped, serialized, and moved across the network, process, and storage boundaries: payload shape and size, zero-copy or borrow-based deserialization, schema-evolution cost, compression, whether transformations happen at the right layer (server vs client, database vs application), and whether the chosen format fits the access pattern. Guidance here shifts fast between library versions — verify against the exact serialization library and framework versions pinned, not the ecosystem in general. Research domain: databases and indexing for wire formats and encodings; systems and storage for serialization at the storage boundary.

**Agent 3 — Queries and Data Access.** Query efficiency, compiled queries vs raw SQL, index utilisation, connection and command lifecycle, pagination approaches, caching strategy, EXPLAIN-plan implications, and the known pitfalls of the specific ORM in use — look up its actual query-translation behaviour for the methods called rather than assuming. Research domain: databases and indexing.

**Agent 4 — Algorithmic and Structural Efficiency.** Time and space complexity, unnecessary iteration or recomputation, data-structure fitness for the access pattern, caching of expensive computations, lazy vs eager evaluation; on the frontend, reactive dependency chains, computed-property efficiency, and reconciliation cost. **Boundary**: expressiveness and correctness of data-shape design (illegal-state-unrepresentable, discriminated unions, newtypes, redundant representations) is `/review` Agent 1's lens — keep findings here framed around access-pattern fitness, complexity class, or allocation/reconciliation cost. If a finding is about how a type *models the domain* rather than how it *performs under access*, it belongs in `/review`. Research domain: algorithms and data structures.

**Agent 5 — Async and Concurrency Architecture.** Task topology (independent I/O awaited in series, CPU-bound work blocking the async runtime), spawn discipline (tracked join handles vs fire-and-forget, bounded concurrency via semaphores or bounded channels), synchronization-primitive fitness (exclusive vs read-write vs lock-free atomics vs channels, critical-section scope, locks held across await points), backpressure and flow control (bounded channels, producer backpressure, pool sizing, unbounded queue growth under load), cancellation and graceful-shutdown drain, runtime configuration (blocking calls dispatched off the async pool, thread-pool sizing), and contention hotspots amenable to sharding or thread-local caching. Severity calibration for this lens: **critical** = blocking the async runtime, unbounded resource growth under load, data races, deadlock potential, sequential I/O that should be concurrent; **warning** = suboptimal primitive selection, missing cancellation support, fire-and-forget without backpressure bounds; **suggestion** = tighter lock scope, lock-free alternative, runtime tuning. Research domain: concurrency and parallelism; systems and storage for scheduler, runtime and backpressure design.

## Step 2.5: Vet agent output (orchestrator)

Invoke the `flow-contract-vet-research` skill to load the universal vet-pass procedure (triage by source+evidence-grade, `ESCALATE-TO-DEEP` honouring, drop-low-confidence rule, spot-check sampling, drop/downgrade-with-rationale, the canonical `[[vet_events]]` append — one `tomlctl array-append <ledger> vet_events` call per agent, its fields passed as `--set` / `--set-json` flags and any prose `rationale` through `--set-file` — the mandatory `vet: Agent-{n} (<lens>) — N sampled, M dropped, K downgraded` console line, and the >30% systemic-failure re-dispatch rule).

**Sample size**: the skill's default. Lens names for the console line: `memory`, `serialization`, `queries`, `algorithm`, `async`. Per sampled finding, additionally verify the Counter line is plausible. **Expand-on-failure is stricter here than in `/review`**: a sampled finding that is dropped — a fabricated anchor, a claim the code contradicts — expands the sample to *all* of that agent's findings, because `/optimise` dispatches all-deep and has no cheaper tier to fall back on. A downgrade alone does not expand it. Even deep agents produce wrong findings, and vetting is what makes the deep dispatch worth its cost — it turns a probabilistically-correct sample into a verified one. **Vet pass is NOT optional** — the Step 1 idempotency guards prevent duplicate-flagging but cannot retroactively remove a fabricated finding once it is persisted; that needs manual cleanup via `/optimise-apply` or hand-editing. Vet first, persist second.

## Interim checkpoint

After Step 2.5 vetting, persist surviving items (plus any reopened items from the Step 1 deferred-reopen sweep) to the ledger in a single atomic `tomlctl items apply <ledger> --ops '@<path>' --id-prefix O --on-stale skip --no-stamp` call, its ops staged with the Write tool. Its add ops carry no `id`: `--id-prefix O` mints them under the write lock and the envelope lists them as `ids`. When the checkpoint holds only adds, `tomlctl items add-many <ledger> --id-prefix O --no-stamp --ndjson <path>` does the same. Record the ids the checkpoint mints. Each reopen op carries `"expect": {"status": "deferred"}`, the status the sweep read; report any `skipped_stale` ids on a `changed during the run` line and do not retry them — the current value wins. Always pass `--on-stale skip` with `expect`; an older tomlctl ignores `expect` alone but rejects the unknown flag. An interrupted run — Ctrl-C between agent return and the Step 3 render — would otherwise lose the research output; writing here makes findings durable the moment they exist, and the Step 1 idempotency guards make a re-run safe (worst case is re-rendering a report from an already-checkpointed ledger). Defer two writes to Step 3: the `last_updated` bump — the checkpoint passes `--no-stamp`, because the ledger is only "fresh" once the report was actually produced — and `rounds` increments on existing open items (they only matter once the report includes them). Skip the checkpoint entirely when the run's own pending set is empty — no surviving findings and no reopen or user-input ops to persist; the gate needs no tomlctl call and never emits an empty `--ops` payload.

## Step 3: Produce Findings Report

**Reason thoroughly through consolidation.** Cross-reference all five agents' findings, dedupe within the run (several lenses flagging one issue become a single record noting which lenses caught it), validate the severity classifications, resolve conflicting recommendations, and confirm the evidence is sound. Capture inconclusive research or unclear tradeoffs in `description`. An empty finding set is valid — not every change has optimisation opportunities. Do not suggest optimisations that trade readability for negligible gain.

**Cross-cutting concurrency review** — after the in-run merge, look for emergent concerns no individual agent could see: lock ordering across multiple acquisitions (deadlock risk), the combined effect of multiple spawn points on task count under load, sequential operations spread across different files that could be joined at a higher level (independent I/O in one handler), and whether components shut down in dependency order.

Merge into the ledger per the dedup / merge / regression rules in the `flow-contract-ledger-schema` skill: a finding matches an existing item iff same `file` AND (same non-empty `symbol` OR exact `summary` match); unmatched findings get `O{n}` IDs minted by tomlctl (starting at `O1`; never computed by hand, never renumbered — see the persist step below); a match on an `open` item that existed before this run (the open-match set excludes the ids this run's Interim checkpoint minted) reuses the ID, increments `rounds`, refreshes drifted `line`, and updates `description` / `evidence` when this round produced richer material, leaving `first_flagged` untouched; a match on an `applied` item is a **regression** — new ID with `related = ["<old id>"]`, flagged prominently; matches on `deferred` / `wontapply` / `verified-clean` are noted in the console and not re-reported. Chronic items (`rounds >= 3`, still open) get a dedicated escalation callout. After reading the ledger, compare `last_updated` against today plus the latest in-scope commit from `git log -1 --format=%cI`: if it is more than a day ahead of both, emit `ledger last_updated=<date> is future-dated; treating as today for filter purposes` and use today for legacy-numeric selector resolution — do not error, but do not let a future date silently drop items from `/optimise-apply`'s latest-report filter either.

Persist via the skill's write pattern in one batched call: `tomlctl items add-many <ledger> --id-prefix O --ndjson <path>` (pure-add — the common case for new findings, with `first_flagged` / `rounds` / `status` in `--defaults-json`) or `tomlctl items apply <ledger> --ops '@<path>' --id-prefix O` (heterogeneous adds plus `rounds` / `line` / `description` / `evidence` updates), the payload staged with the Write tool per the tomlctl skill — never loop per-item `items update` calls. Either way rows and add ops carry no `id`; `--id-prefix O` mints them and the envelope lists the minted `ids`. Every `update` op on an existing item carries `"expect": {"status": "open"}` and the batch passes `--on-stale skip`: a human (glimpse) or another run may have dispositioned the item since it was read. Report any `skipped_stale` ids on a `changed during the run` line and do not retry them. The batch stamps `last_updated` itself, completing the bump the checkpoint deferred; no second write follows. When Step 3 lands nothing — the merge left nothing to persist, or every op came back `skipped_stale` — no write stamps the ledger, so close the run with `tomlctl set <ledger> last_updated "$(date -u +%F)"`: the shell supplies today's UTC date, the date a stamping write would have set, and the apply flow's freshness gate and latest-report filter then see the run that just completed. Skip it whenever a Step 3 write changed the ledger; that write already stamped it. Preserve `schema_version` verbatim and follow the key-order convention. **Do NOT delete the ledger file** — stable `O`-IDs, `rounds`, and disposition history persist across runs, and `/optimise-apply` mutates statuses in place through this same contract rather than consuming the file.

Render the merged ledger state as grouped markdown tables **inline in console output only, never persisted** (the TOML on disk is the authoritative artifact), with the resolved ledger path in the report header so `/optimise-apply` can locate it. Group as: **New this run**, severity-grouped Critical / Warnings / Suggestions, each row carrying ID, `file:line` (or `file:symbol` when the line has drifted), category, summary, effort; **Recurring** (`rounds >= 2`, still open) as a dedicated sub-group emphasising chronic items at `rounds >= 3`; **Regressions**, listing new ID, previously-applied ID, and summary; and one-liners for existing non-open matches ("matches existing `<status>` item `<id>`, not re-reporting"). Pattern findings persist with their `instances`, `sweep` and `enumeration` fields; the apply flow budgets on that declared set, so an instance dropped here is a file the implementer cannot touch. Findings the agents tagged `needs-plan` are minted normally but rendered in their own **Needs a plan** group with a `/plan-new` suggestion and left out of the apply prompt: the tag means several decisions, ordered steps or dependent parts that must move together, never breadth alone, and a wontapply written for scope is a routing failure, not a disposition. Render an item's `description` below the table for anything the user is likely to act on (typically critical and warnings) rather than inlining the full body into every row. Then prompt: *"Run `/optimise-apply` to implement these findings, or select specific items by ID (e.g. `/optimise-apply O1,O3,O5`). Legacy positional selectors (`/optimise-apply 1,3,5`) still work and resolve against this run's report."*

**Observations outside the ledger's scope.** An agent finding whose `file` lies outside the optimise scope, and a cross-cutting observation that is not a finding against an in-scope file, are neither: do not mint an `O{n}` for them, and do not force a terminal disposition onto an item the ledger never owned. Capture each in the backlog instead, alongside every `TANGENTIAL:` line the lens agents returned: run the `backlog-capture` skill's check-then-add gate on each candidate, minting with `--origin optimise --flow <slug>`, and list the resulting ids on a `Backlog` line in the console report.
