# /review — code review across five lenses

> Skim-readable orchestrator. Full contract bodies load on demand via skill invocations.

Reviews code through five (or six) parallel lenses — Quality, Security, Architecture, Completeness, Testability (plus conditional Package Quality for `claude/commands/` and `claude/skills/` paths). Findings persist to a TOML ledger keyed by stable `R{n}` IDs; re-runs dedupe, merge, escalate chronic items, and surface regressions. Targeted mode takes paths/feature names as `$ARGUMENTS`; with no args, scope is derived from recent git changes.

> **Effort**: Requires `xhigh` or `max` — lower effort may reduce agent spawning and tool usage.

## Step 0: Pre-flight (flow resolution + doctor)

Invoke the `flow-contract-flow-context` skill to load the flow-bootstrap envelope contract (input/output shapes, `envelope.ok` gating, `envelope.resolved.*` and `envelope.doctor.*` binding rules, no-flow fallback, doctor-fail handling, staleness reconciliation, and the mandatory bootstrap-summary console line).

Build the input envelope:

```bash
tomlctl flow envelope build \
  --command review \
  --branch "$(git branch --show-current)" \
  --worktree "$(git rev-parse --show-toplevel)" \
  --cwd "$(pwd)" \
  --staleness-threshold 7d
```

The block above is complete and copy-pasteable as-is — do NOT look up `--help`; `/review` lazily creates its ledger, so no `--require-artifact` flag is needed, and `--staleness-threshold 7d` is the default, passed explicitly for clarity. On detached HEAD, `git branch --show-current` prints an empty string; omit the `--branch` flag in that case so the envelope records `branch:null` rather than `branch:""`.

Pass `--flow-override <slug>` to the envelope build when the user supplied `--flow`, and `--path-arg <p>` once per `$ARGUMENTS` path token. Dispatch `flow-bootstrap` via the Task tool with `subagent_type: "flow-bootstrap"` and the printed JSON as the prompt. Gate on `envelope.ok`; bind `slug`, `context_path`, `artifacts.*`, `doctor.ok`, and `resolved.stale` for downstream phases. Emit the bootstrap-summary line before any other action. When staleness fires for `/review`, invoke the `plan-update` skill with literal arg `reconcile` before continuing.

**User inputs.** Invoke the `flow-contract-user-inputs` skill and run its Step-0 sweep with `--ledger review` and `--by review`, selecting on the bound `slug`, or for a flow-less run on the `<scope>` Step 1 derives, so a flow-less sweep completes once Step 1 has resolved the ledger path. Fold each kept `note` into the Step 2 preamble as quoted user-supplied data. Each `request` this carrier can honour — `deferred`, `wontfix`, `verified-clean`, or reopening a `deferred` item, with the companion fields the ledger-schema skill requires taken from the record's text — becomes an op in the Interim checkpoint batch carrying `"expect": {"status": "<status read>"}`, and counts as a pending transition for that checkpoint's skip gate. Decline a request for `fixed`, which lands only with the fix. Handle every acknowledged record before the Step 3 report.

## Step 1: Determine Scope and Load Prior Findings

Identify in-scope files from `$ARGUMENTS` (paths / globs / feature names) or — when empty — from git diff against the merge-base (feature branch) or `HEAD~1` (main). Before treating a token as a path arg, check it against `tomlctl flow list`: if a `$ARGUMENTS` path token exactly matches the `slug` of a row in its `flows` array, treat it as `--flow-override` (route it to the Step-0 envelope build) rather than passing it as a `--path-arg`. This prevents a bare flow-slug argument from being misread as a path while the resolver silently auto-picks the wrong flow via active-latest. Enforce the scope-input safety invariant: reject `..` traversal, refuse absolute paths outside the worktree, cap glob breadth ≤ 200 matches. Classify each file by area (backend / API / frontend / infra / config / test). When scope > 10 files, delegate per-file classification to a `subagent_type: "Explore"` agent (`thoroughness: "quick"`) and keep only the ≤ 600-word summary table. Dispatch it one-shot — **never pass `name:`**: a named spawn becomes a teammate with no return channel, and the built-in `Explore` carries no teammate-delivery instruction, so the table is lost and you get only a "Teammate @x finished" notification. Treat that as a failed dispatch and re-dispatch unnamed rather than pumping it with `SendMessage`.

Invoke the `flow-contract-ledger-schema` skill to load the canonical ledger schema (field set, disposition vocabulary, dedup rules, read/write contract via `tomlctl items` / `array-append`, key-order convention, rollback / vet event logs). Resolve the ledger path: `envelope.resolved.artifacts.review_ledger` when a flow resolved, else `.claude/reviews/<scope>.toml` (derive `<scope>` from path arg / feature name / branch / `recent`). Load via `tomlctl items list <ledger> --status open --verify-integrity` (or treat as first review when the file is missing). Extract items whose `file` overlaps current scope as the **prior findings context** — agents use this to skip already-resolved items, flag regressions, and avoid re-reporting open items. Load `deferred` and `wontfix` items overlapping scope as well, with their `defer_trigger` or `wontfix_rationale`: the consolidation step already refuses to re-mint a match on those, but an agent that never saw them spends its budget rediscovering them, and the rationale is what tells it the class is settled.

**Dev server, for frontend scope.** When any in-scope file classifies as frontend and the project's `.mcp.json` declares the `playwright` server, probe the dev URL the project documents (its CLAUDE.md, or the dev script in its manifest) and embed `DEV SERVER: <url>` in the preamble when it answers, `DEV SERVER: none` when it does not. The browser serves Agents 4 and 5, so name it in those two lens prompts. Detect only: the review starts no server and no lens agent may. When nothing answers and the project documents a dev command, ask once whether the user will start it — a user-engagement gate the autonomy directive does not override, skipped on a non-interactive run — and re-probe on the reply.

**Lint baseline, once.** Run the project's declared lint or type-check (the `Build & test` section of its CLAUDE.md, or the plan's `## Verification Commands`) one time here and keep the diagnostics that touch in-scope files as a `LINT BASELINE` fence for every prompt. A candidate the linter already reports is not a finding, and six agents each running the check in parallel serialise on one build lock. When no lint command is declared, embed `LINT BASELINE: not run — no lint command declared` so an absent fence is not mistaken for a clean one.

Invoke the `backlog-capture` skill for the repo-scoped capture store's discipline, then load its live rows (`open` and `promoted`) alongside the ledger's (drop `--area-prefix` when the scope is not a single directory):

```bash
tomlctl backlog list --live --area-prefix <scope-dir>
```

Hand each returned row's `summary` and `context` to the lens agents as prior context: a row is a known repo-scoped issue plus how to work around it, so an agent tripping over the same thing does not spend the round rediscovering it. A `promoted` row is already claimed by the flow its `promoted_to` names: do not re-raise it as a new finding unless that flow is at `review` or `complete` or does not exist, and in that case point the user at `/backlog` to re-triage it.

Invoke the `flow-contract-ledger-disposition-sweep` skill to load the orphan-surfacing and deferred-reopen sweep contracts. Run both before the agent dispatch: orphan-surface read-only via `tomlctl items orphans <ledger>`; deferred-reopen is **a user-engagement gate — the autonomy directive does not apply** (every reopen passes through the per-item prompt; non-interactive invocations surface candidates only and never mutate).

## Step 2: Launch Parallel Review Agents

Launch **all** agents in a single response message via the Agent tool — concurrent execution is mandatory. Mixed-tier dispatch is non-negotiable: Agents 1 (Quality), 2 (Security) and 3 (Architecture) use `subagent_type: "research-deep"` (judgement-licensed); Agents 4 (Completeness), 5 (Testability), 6 (Package Quality, conditional) use `subagent_type: "research-lite"`. The conditional 6th lens fires when any in-scope path begins with `claude/commands/` or `claude/skills/`. Each agent receives a **byte-identical literal preamble** (prompt-cache reuse — whitespace differences defeat it): the file list and classification, the project's CLAUDE.md conventions and constraints excerpt, the ledger path, which also opens the prompt as a line of its own at column 0 in the form `ledger: <repo-relative ledger path>` (path only, no item ids, and emitted for a flow-less ledger too, where it goes unattributed), the prior-findings context including the deferred and wontfix items with their rationale, the backlog rows, the `LINT BASELINE` fence, and the `DEV SERVER` fence when Step 1 set one; the lens divergence, the ledger field set and the budget follow below a clear divider. The agents load the `research-methods` skill themselves, so do not restate its method in the prompt: the prompt's job is the lens, the context and the budget. Each returns **up to 20 findings, target 15 — a ceiling and a target, never a quota**. Findings carry the ledger-schema field set (no `id` / `first_flagged` / `rounds` / `status` — those are assigned in Step 3). Security caps hard at 5. Agent 5 owns the testing lens; Agent 4 defers tests-not-written observations to Agent 5. Agent 3 owns the `db` category. Do NOT silently downgrade the judgement-licensed agents to `research-lite`.

The six lenses. Each names what it owns and what it does not flag; the dispatch prompt carries this text, since a lens named without its contract is a lens the agent resolves for itself.

- **Agent 1 — Quality, DRY, Idioms & Type Design** (`research-deep`, category `quality`). Internal consistency against the patterns the codebase actually uses: search for sibling logic before calling something novel, and read history before calling something drift, because consistency beats modernity unless the project is migrating. Idiomatic use of the language and framework: builtins over reimplementation, type-system features used rather than worked around, the framework's intended patterns followed. Type-design expressiveness as a correctness concern: illegal states made representable by boolean and optional combinations, domain-meaningful primitives crossing boundaries untyped, redundant or derivable fields, stringly-typed closed sets. Access-pattern fitness belongs to `/optimise` Agent 4. Do not flag style differences that leave readability intact, single-use helpers that aid clarity, or divergence a comment or ADR explains.
- **Agent 2 — Security & Trust Boundaries** (`research-deep`, category `security`, hard cap 5). Essentials and quick wins for the boundaries the changed code introduces: where untrusted data enters, what it reaches, and what asserts it on the way. Real risks with a plausible vector in the actual deployment only; no threat-model dumps, defence-in-depth lists or theoretical items. Advisory lookups cover only the dependencies the in-scope changes add or bump: a whole-lockfile sweep would spend the cap of 5 that trust-boundary findings need, and the project's own audit command owns the full tree.
- **Agent 3 — Architecture, Structure & Domain Modelling** (`research-deep`, owns category `db`). Logic in the right layer, separation of concerns, and whether the change makes the codebase harder to evolve. New or moved files placed and named per the layout and module-boundary patterns the tree establishes, inspected rather than assumed. Domain modelling and persistence boundaries as `db`: persistence concerns leaking into domain types, a single type serving request, wire and storage roles, aggregate references held by object rather than identity, relationship cardinality that contradicts the domain, migrations that change stored shape without a data step. Do not flag documented pragmatic shortcuts, coupling confined to one module, or a placement no existing file contradicts.
- **Agent 4 — Completeness & Robustness** (`research-lite`). Does the work feel finished: unhandled edge cases and error paths, partial implementations, loose ends, and everything that should have changed alongside what did, including callers, docs, config, migrations and string literals that name the changed thing. Grep every renamed or removed symbol across the whole tree, prose and literals included. Defer tests-not-written observations to Agent 5. Do not flag defensive checks the framework already guarantees or TODOs tracked elsewhere.
- **Agent 5 — Testability, Diagnostics & DX** (`research-lite`, category `testability`, owns the testing lens). Seams: hidden globals, hard-wired concretes, time, randomness and IO without injection points. Tests that are deterministic, named for the behaviour they cover, and aimed at the specific regression risk the change carries rather than coverage for its own sake. Error messages that name the operation, the input and expected versus actual; log levels that fit; help text and defaults a first-time user can discover. Do not flag trivial accessors, debug-log gaps on paths the project does not already log, or DX polish on internal-only surfaces.
- **Agent 6 — Package Quality** (conditional, `research-lite`, category `package-quality`). Static analysis of the harness files in scope: frontmatter present and descriptive (`description` and `argument-hint` for commands, `name` and a trigger-bearing `description` for skills), section headers present and ordered with no broken cross-references, every phase substantive rather than a stub, terminology consistent with the shared blocks, and any block named in `scripts/shared-blocks.toml` byte-identical to its peers. Dedup against Agent 1 on `(file, symbol)`: `package-quality` is the canonical reporter for these paths.

## Step 2.5: Vet agent output (orchestrator)

Invoke the `flow-contract-vet-research` skill to load the universal vet-pass procedure (triage by source+evidence-grade, `ESCALATE-TO-DEEP` honouring, drop-low-confidence rule, spot-check sampling, drop/downgrade-with-rationale, the canonical `[[vet_events]]` append — one `tomlctl array-append <ledger> vet_events` call per agent, its fields passed as `--set` / `--set-json` flags and any prose `rationale` through `--set-file` — the mandatory `vet: Agent-{n} (<lens>) — N sampled, M dropped, K downgraded` console line, and the >30% systemic-failure re-dispatch rule).

**Per-carrier sample sizes**: the skill's default, raised to ≥ 5 findings (or all if fewer) for `architecture`, `completeness` and `package-quality` — the lenses whose findings fail vetting most often, whatever their tier. Lens names for the console line: `quality`, `security`, `architecture`, `completeness`, `testability`, `package-quality`. **Vet pass is NOT optional** — the Step 1 idempotency guards cannot retroactively remove a fabricated finding once persisted.

## Interim checkpoint

After Step 2.5 vetting, persist surviving items (plus any reopened items from the Step 1 deferred-reopen sweep) to the ledger in a single atomic `tomlctl items apply <ledger> --ops '@<path>' --id-prefix R --on-stale skip --no-stamp` call, its ops staged with the Write tool, so an interrupted run doesn't lose agent output. Its add ops carry no `id`: `--id-prefix R` mints them under the write lock and the envelope lists them as `ids`. When the checkpoint holds only adds, `tomlctl items add-many <ledger> --id-prefix R --no-stamp --ndjson <path>` does the same. Record the ids the checkpoint mints. Each reopen op carries `"expect": {"status": "deferred"}`; report any `skipped_stale` ids on a `changed during the run` line and do not retry them. Defer the `last_updated` bump and `rounds` increments on prior open items to Step 3: the checkpoint passes `--no-stamp`, so an interrupted run does not mark the ledger fresh. Skip the checkpoint when the run's own pending set is empty — no surviving findings and no reopen or user-input ops to persist; the gate needs no tomlctl call.

## Step 3: Consolidate and Persist

Cross-reference all agent results; apply the dedup, merge, and regression rules per the ledger-schema skill (same `file` AND (same non-empty `symbol` OR exact `summary` match)). New findings get `R{n}` IDs minted by tomlctl — never computed by hand, never renumbered (see the persist step below). Regressions against `fixed` items get a new ID with `related = ["<old id>"]`. Open-item matches reuse the existing ID and increment `rounds`; the open-match set excludes the ids this run's Interim checkpoint minted, so the merge and `rounds` increment apply only to items that existed before this run. Chronic items (`rounds >= 3` post-merge) MUST be called out in a dedicated escalation callout; `rounds >= 5` items get a concrete defer-or-wontfix recommendation in the callout.

Render the merged ledger state as severity-grouped markdown tables (Critical / Warnings / Suggestions) plus Still-Open / Resolved-Since / Regressions sub-groupings — **rendered inline in console output only, never persisted**. Persist the merged state per the ledger-schema skill's write pattern in one batched call for all mutations: `tomlctl items add-many <ledger> --id-prefix R --ndjson <path>` (pure-add) or `tomlctl items apply <ledger> --ops '@<path>' --id-prefix R` (mixed), the payload staged with the Write tool. Either way rows and add ops carry no `id`; `--id-prefix R` mints them and the envelope lists the minted `ids`. The write stamps `last_updated` itself, completing the bump the checkpoint deferred. When Step 3 lands nothing — the merge left nothing to persist, or every op came back `skipped_stale` — no write stamps the ledger, so close the run with `tomlctl set <ledger> last_updated "$(date -u +%F)"`: the shell supplies today's UTC date, the date a stamping write would have set, and the apply flow's freshness gate and latest-report filter then see the run that just completed. Skip it whenever a Step 3 write changed the ledger; that write already stamped it. Every `update` op on an existing item carries `"expect": {"status": "open"}` and the batch passes `--on-stale skip`: a human (glimpse) or another run may have dispositioned the item since it was read. Report any `skipped_stale` ids on a `changed during the run` line and do not retry them. After the report, prompt the user with a concrete `/review-apply R{a},R{b}` invocation for the lowest-hanging quick wins, plus disposition syntax (`defer R{n} — reason — trigger`, `wontfix R{n} — rationale`). Pattern findings persist with their `instances`, `sweep` and `enumeration` fields; the apply flow budgets on that declared set, so an instance dropped here is a file the implementer cannot touch. Findings the agents tagged `needs-plan` are minted normally but rendered in their own **Needs a plan** group with a `/plan-new` suggestion and left out of the quick-wins line: the tag means several decisions, ordered steps or dependent parts that must move together, never breadth alone, and a wontfix written for scope is a routing failure, not a disposition.

**Observations outside the ledger's scope.** An agent finding whose `file` lies outside the review scope, and a cross-cutting observation that is not a finding against an in-scope file, are neither: do not mint an `R{n}` for them, and do not force a terminal disposition onto an item the ledger never owned. Capture each in the backlog instead, alongside every `TANGENTIAL:` line the lens agents returned: run the `backlog-capture` skill's check-then-add gate on each candidate, minting with `--origin review --flow <slug>`, and list the resulting ids on a `Backlog` line in the console report.

## Step 4: Handle Dispositions (if user responds)

**This is a user-engagement gate — the autonomy directive does not apply.** Apply dispositions only when the user replies with conversational commands in the same turn. Recognise `defer R{n} — reason — trigger` (set `status = "deferred"` + `defer_reason` + `defer_trigger`), `wontfix R{n} — rationale` (set `status = "wontfix"` + `wontfix_rationale`), and `fix R{n}` (route to `/implement` with the item's `file` / `line` / `summary` / `description` — **do NOT mutate status here**; the `fixed` transition happens when the fix actually lands).

Apply all dispositions in the reply as a single atomic batch via `tomlctl items apply <ledger> --ops '@<path>' --on-stale skip`, the ops written to a file with the Write tool even for a single disposition — a staged file never passes the user-supplied reason, trigger and rationale strings through shell quoting. Every disposition op carries `"expect": {"status": "open"}`, the status the report showed: a human (glimpse) or another run may have changed the item since. Report any `skipped_stale` ids on a `changed during the run` line, naming the status each was found in, and do not retry them — the current value wins. Always pass `--on-stale skip` with `expect`; an older tomlctl ignores `expect` alone but rejects the unknown flag. The batch stamps `last_updated` itself; no second write follows. Suggest `/review-apply` for the next round of automated fixes; `/implement` remains available for plan-task-driven work.
