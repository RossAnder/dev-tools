---

**Vet research-agent output (orchestrator).** This block defines the universal vet-pass procedure the orchestrator runs after research-agent dispatch returns. The build/test verification agent catches code-shape failures, but it does NOT catch fabricated `file:line` references, made-up library version pins, or low-confidence claims dressed up as fact in research output. The vet pass is the gate that distinguishes "research returned" from "research findings are trustworthy."

1. **Triage by source agent + evidence-grade.** Group findings by `(agent_index, evidence-grade)`; emit a one-line summary per group to console.
2. **Honour `ESCALATE-TO-DEEP` flags.** If any agent prefixed its return with `ESCALATE-TO-DEEP: <reason>`, re-dispatch that lens to `research-deep` with the escalation reason in the prompt before further vetting that lens's output.
3. **Drop unverified `low` / `low-confidence` findings** unless explicitly framed as a hypothesis with a concrete verification step. Drop any finding with no Counter line or no anchor (`file:line` plus symbol, or URL plus version), and any finding matching a `deferred` or `wontfix` / `wontapply` item whose trigger has not fired. A return with no coverage line is noted in the console line as `no coverage line`, and one that cites a source beyond the tree with no `Searched:` line as `no search log`; neither is re-dispatched for that alone, but each omission counts toward the systemic-failure threshold in step 8.
4. **Spot-check sampled findings.** Sample at least 3 findings per agent, or all if it returned fewer; a carrier states only where it departs from that, per lens. Draw the sample from `medium` and `low` findings first and reach `high` only after them. A sampled `high` finding that quotes the code at its `file:line` gets a one-line Grep for the quoted text in that file instead of a full read — a hit at the cited line confirms the anchor, anything else fails it. For every other sampled finding: read the cited `file:line`, confirm the code matches the description, verify any cited URLs and Context7 IDs, and check every version pin against the lockfile. An anchor inside an installed dependency (registry source, `node_modules`) is read like any other `file:line`, and the version it sits under must be the locked one. For an advisory id (OSV, GHSA, RUSTSEC, CVE), re-fetch `https://api.osv.dev/v1/vulns/<id>` and drop the finding when its affected ranges exclude the pinned version. Downgrade a claim about what is latest or current when the newest source its `Searched:` line records predates your knowledge cutoff, unless the finding frames the claim as of that date. When the Details report a disagreement between sources, the Counter line must name the losing source; downgrade the finding if it does not. For a pattern finding, re-run its `sweep` strings with `tomlctl sweep -e <string> [-e <string>…]` (each string verbatim) and compare the returned `file:line` hits against `instances`: a site the sweep finds that the finding omits is added, and a finding whose recorded sweep finds materially fewer sites than it claims is downgraded with the observed count as the rationale. The vet runs before the interim checkpoint persists the finding, so the standalone verb — which needs no ledger — is the vet-time re-run; once the checkpoint has written the item, `tomlctl items sweep <ledger> --ids <id>` re-checks it from the stored `sweep` array and reports the diff per anchor: `new` sites the item omits (add them), `gone` anchors the sweep no longer hits (downgrade with the observed count), `unverified` anchors the sweep could not judge, each with the `reason` why (neither confirmed nor refuted, so never a downgrade on its own). Both forms are read-only; never pass `--update` here, because a finding under vet is not yet accepted and rewriting its `instances` belongs to the apply flow's pre-analysis. On an older binary predating `sweep`, fall back to re-running the strings by hand with `Grep` and comparing the hit set against `instances` until `cargo install --path tomlctl`. The re-run is one search; it is what turns a claimed enumeration into a verified one.
5. **Drop or downgrade findings that fail vetting**, with rationale. Downgrade by appending `_orchestrator-downgrade: <reason>` to the evidence-grade line.
6. **Append a durable `[[vet_events]]` entry to the ledger** via the canonical heredoc form — one entry per vetted agent, the `agent_index` field discriminates:

   ```bash
   cat <<'EOF' | tomlctl array-append <ledger> vet_events --json -
   {"timestamp":"<ISO 8601>","command":"<review|optimise|review-plan|plan-new|plan-update|test-bootstrap>","agent_index":<n>,"lens":"<lens>","tier":"<lite|deep>","sampled_count":<N>,"dropped_count":<M>,"downgraded_count":<K>,"dropped_ids":["<R{n}>",...],"rationale":"<≤8 KiB rationale>"}
   EOF
   ```

   `array-append` is a `mutate_doc*`-routed verb, so this idiom works against a fresh (missing) ledger too — the first `vet_events` append auto-creates the file with the `schema_version = 1` skeleton, no pre-initialisation needed. The append stamps the ledger's `last_updated` itself, so no follow-up `tomlctl set` is needed.

   `lens` is the carrier's canonical lens name exactly as it lists it — lowercase and hyphenated (`package-quality`, never `Package Quality` or `Agent-6`), so entries from different runs aggregate by string. `tier` is the tier of the run whose findings were vetted: `deep` for a `research-deep` dispatch or a lens re-dispatched to it under step 2, `lite` otherwise.

   Every `vet_events` field is inline in the heredoc above — do **not** load the `flow-contract-ledger-schema` skill to write one. Consult it only if you need the full ledger schema for some other reason.
7. **Emit the mandatory console line per agent**: `vet: Agent-{n} (<lens>) — N findings sampled, M dropped, K downgraded`. The format is fixed; `<lens>` is the same canonical string the entry's `lens` carries.
8. **>30% systemic failure rule.** If more than 30% of an agent's findings fail vetting, re-dispatch that lens with the failure pattern in the prompt. For `research-lite` agents, the re-dispatch SHOULD escalate to `research-deep` (the systemic failure indicates the lens is too judgement-heavy or fabrication-prone for a fetch-and-summarise pass on this profile).
