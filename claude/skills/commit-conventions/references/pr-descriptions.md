# PR Descriptions

## One-sentence opener

The first sentence of every PR description states the user-visible effect — what changes for someone using the product, not what the code does internally.

- Good: "Users can now sign in with passkeys on mobile devices."
- Bad: "Adds WebAuthn endpoint and updates the auth middleware."

The opener answers "what does this change for a user?" If no user-visible effect exists
(pure refactor, test addition, CI change), lead with the operational effect instead:
"CI pipeline now caches Cargo registry between runs, cutting cold-build time by ~40%."

## Commits

When the PR has more than 3 commits, render the commit subjects as a bulleted list under a `## Commits` heading so reviewers can scan the change set without running `git log`:

```
## Commits

- Add passkey credential creation endpoint
- Wire WebAuthn library into the auth middleware
- Add integration tests for passkey sign-in flow
- Update API docs with passkey endpoints
```

For 3 commits or fewer, narrate them in prose — a bulleted list at small N adds visual
noise without scan benefit: "This PR adds the WebAuthn endpoint, wires it into the auth
middleware, and adds smoke tests."

## Reviewer attention

Include a `### Reviewer attention` subsection when the change touches performance-sensitive,
security-sensitive, or migration-bearing code. Only include the tags that apply; omit
the subsection entirely if none apply.

```
### Reviewer attention

- **Perf**: credential lookup now runs on every request — benchmark result in CI shows p99 < 2 ms under 500 RPS.
- **Security**: private key material never leaves the HSM; the new endpoint returns a challenge token only.
- **Migration**: adds `webauthn_credentials` table — migration runs automatically on deploy; no manual step required.
```

## Issue linkage

When the PR closes a tracked issue, include a `Fixes:` line so GitHub auto-closes it on merge:

```
Fixes: #42
```

Multiple issues on one line:

```
Fixes: #12, #15, #18
```

`Closes:` and `Resolves:` are equivalent aliases — all three trigger GitHub's auto-close.
Pick one and use it consistently. Place the line at the end of the description, after the
prose and after `### Reviewer attention` if present.

## Attribution

Do NOT add `Co-Authored-By:` trailers or "Generated by Claude" banners to PR descriptions.
Attribution is configured once in `claude/settings.json` under the `attribution.pr` key and
applied automatically by the tooling — the PR body itself stays free of those markers.
Adding them manually creates duplicates and leaks implementation details into the
public-facing description.
